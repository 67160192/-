ส่วนที่ 4: ข้อสอบจำลองตอนที่ 3 (ตอบโดยย่อ)

ข้อ 1. ทำไม Usability Testing กับผู้ใช้ประมาณ 5 คนจึงมักเพียงพอ และการเพิ่มผู้ทดสอบเกินนี้ให้ผลอย่างไร

ดูแนวคำตอบ

งานวิจัยของ Nielsen (1994) ชี้ว่าผู้ทดสอบ 5 คนค้นพบ usability problem ได้ราว 85% เพราะปัญหาส่วนใหญ่ซ้ำกันข้ามผู้ทดสอบ เมื่อเพิ่มคนมากกว่า 5 คนจะพบปัญหาใหม่น้อยลงเรื่อย ๆ (diminishing returns)

ข้อ 2. เหตุใดจึงต้องดึงราคาสินค้า (unitPrice) จากฐานข้อมูลฝั่ง server แทนการรับจาก req.body

ดูแนวคำตอบ

ค่าที่มาจาก client สามารถถูกแก้ไขได้ เช่น ผู้ใช้ส่งราคาเป็น 1 บาท ระบบจะคิดเงินผิดโดยไม่มีใครตรวจพบ การดึงราคาจากฐานข้อมูลฝั่ง server ทำให้ราคาถูกควบคุมโดยระบบเพียงแห่งเดียว

ข้อ 3. Architecture Diagram ควรตรวจสอบกับโครงสร้าง repository จริงอย่างไร และการวาด diagram ให้ดูสมบูรณ์เกินกว่าโค้ดจริงรองรับก่อให้เกิดปัญหาอะไร

ดูแนวคำตอบ

Architecture Diagram ต้องสะท้อนสิ่งที่มีอยู่จริงใน repo เช่น โฟลเดอร์ src/routes, src/controllers, src/models หากวาดองค์ประกอบที่ยังไม่มีจริงหรือไม่บอกข้อจำกัดที่รู้อยู่แล้ว ผู้ที่นำ diagram ไปใช้ตัดสินใจต่ออาจเข้าใจผิดว่าระบบรองรับสิ่งนั้นแล้ว

ส่วนที่ 5: กรณีศึกษา (ตอนที่ 4 จำลอง)

สถานการณ์: ร้านเบเกอรี่แห่งหนึ่งต้องการระบบสั่งซื้อและตัดสต็อกวัตถุดิบ พนักงานหลายสาขาใช้ระบบพร้อมกัน เจ้าของร้านต้องการดูรายงานยอดขายรายเดือนของแต่ละสาขา

จงตอบคำถามต่อไปนี้

  1. เลือก diagram อย่างน้อย 2 ชนิดที่เหมาะกับการออกแบบระบบนี้ พร้อมเหตุผล
  2. ระบุความเสี่ยงด้านความปลอดภัยและการทำงานพร้อมกันอย่างน้อย 2 จุด และเสนอด่านป้องกัน
  3. ออกแบบ test case อย่างน้อย 3 กรณี โดยระบุแหล่งที่มาของแต่ละกรณี (Use Case, Acceptance Criteria, Business Rule หรือ Alt Fragment)
  4. ระบุ usability test หนึ่งข้อ โดยเขียน task เป็นเป้าหมาย และระบุ severity ของปัญหาที่คาดว่าจะพบ
ดูแนวคำตอบ (กรอบการให้คะแนน)
  1. Sequence Diagram สำหรับ flow การสั่งซื้อและตัดสต็อก และ Architecture หรือ Deployment Diagram สำหรับการอธิบายระบบหลายสาขา
  2. Race condition เมื่อหลายสาขาตัดสต็อกพร้อมกัน ด่านป้องกันคือ transaction ร่วมกับ SELECT ... FOR UPDATE / IDOR เมื่อสาขาหนึ่งแก้ไขข้อมูลของอีกสาขา ด่านป้องกันคือตรวจ branch_id ใน WHERE ทุกครั้ง / การรับค่าราคาจาก client ด่านป้องกันคือดึงราคาจาก server
  3. เช่น ตัดสต็อกพอดี, สั่งเมื่อสต็อกไม่พอ (ตรวจ alt), สั่งพร้อมกันสองสาขา (ตรวจ race), รายงานยอดขายแยกตาม branch_id (ตรวจ Use Case รายงาน)
  4. เช่น "สั่งเมนูและยืนยันออเดอร์" ไม่ใช่ "กดปุ่มสีเขียวด้านล่าง" และใช้ severity เป็นตัวจัดลำดับก่อนความถี่

ส่วนที่ 6: เช็กลิสต์ก่อนสอบ

  • อ่านและวาดความหมายของ Lifeline, Activation Bar, Alt และ Loop Fragment ได้
  • อธิบายเหตุผลของ 4+1 View ทั้ง 5 ด้าน และยกตัวอย่างจากโครงงานร้านกาแฟได้
  • บอกได้ว่า IDOR, SQL Injection และ Race Condition คืออะไร พร้อมวิธีป้องกัน
  • อธิบาย Integration Testing กับ E2E Testing ต่างกันอย่างไร
  • บอกลำดับการแก้ bug และนิยาม Refactoring (Fowler, 2018) ได้
  • อธิบายความต่างระหว่าง design (สัปดาห์ 10) กับ validate (สัปดาห์ 12) ได้
